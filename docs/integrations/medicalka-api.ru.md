# Fairhaven Health — API для Medicalka

Документ для интеграционной команды Medicalka.
Версия 1 · 31.07.2026

---

## Базовый адрес

```
https://api.fairhaven.uz/medicalka/v1
```

Только HTTPS. Ответы — `application/json; charset=utf-8`.

## Ключи

Выдаются два ключа с разными правами:

| Ключ | Параметр | Права | Формат |
|---|---|---|---|
| Токен | `?token=` | чтение каталога и остатков (GET) | `fhm_t_…` |
| Секрет | `?secret=` | приём и обновление заказов (POST) | `fhm_s_…` |

Ключ — 49 символов, только `A–Z a–z 0–9 _ -`, экранирование в URL не требуется.

Префикс кодирует назначение: `t` — токен, `s` — секрет. Если ключ отправлен не
в тот эндпоинт, ответ прямо об этом сообщит, а не вернёт безликий 401:

```json
{"code":"mk_unauthorized","detail":"this endpoint expects the token; a secret key was supplied"}
```

Для этого изменения все действующие токены чтения и секреты заказов остаются
действительными и неизменными. Новые ключи не выпускаются, существующие не
ротируются, не отзываются и не меняют формат, способ хранения или имена
параметров. Ранее отозванные тестовые ключи остаются отозванными.

Держите ключи в переменных окружения, не в коде и не в репозитории.

## Шаг 1. Проверка доступа

```bash
curl "https://api.fairhaven.uz/medicalka/v1/pharmacies?token=<ТОКЕН>"
```

```json
{
  "items": [
    { "id": 1, "name": "FAIRHAVEN HEALTH", "created_at": "2026-07-31T09:14:02" }
  ],
  "total": 1
}
```

Филиал один, поэтому `pharmacy_id` при оформлении заказа передавать не нужно.

---

## Типы полей

Совпадают с вашим руководством, повторяем во избежание разночтений:

| Поле | Тип |
|---|---|
| `id`, `product_id`, `pharmacy_id`, `total` | целое число |
| `price`, `quantity` | **строка** с двумя знаками после запятой — `"749000.00"` |
| `updated_at`, `created_at` | строка `YYYY-MM-DDTHH:MM:SS` (UTC, без смещения) |

Для арифметики приводите `price` и `quantity` к числу самостоятельно.

## Шаг 2. Каталог

```
GET /products?skip=0&limit=50
```

`limit` — максимум 1000, по умолчанию 50. `skip` — смещение от начала.

```json
{
  "items": [
    {
      "id": 25432,
      "name": "Fairhaven OvaBoost, №120",
      "manufacturer": "FAIRHAVEN HEALTH",
      "barcode": "895749000851",
      "ikpu": "02106999028000000",
      "package_code": "1490779",
      "images": [
        {
          "url": "https://mini.fairhaven.uz/uploads/1754000000000-a1b2.jpg",
          "hash": "9c1185a5c5e9fc54612808977ee8f548b2258d31"
        }
      ],
      "price": "600000.00",
      "updated_at": "2026-07-24T11:34:43"
    }
  ],
  "total": 42
}
```

Карточка одного товара:

```
GET /products/{id}
```

`total` — общее число доступных вам позиций, а не размер страницы.

### Фискальные коды

| Поле | Что это | Тип |
|------|---------|-----|
| `ikpu` | ИКПУ (MXIK) — код товара в справочнике налоговой | строка из цифр |
| `package_code` | Код упаковки — единица, в которой товар продаётся | строка из цифр |

Оба поля присутствуют в ответе всегда — в `/products`, `/products/search` и
`/products/{id}`. Пустая строка означает, что код по этой позиции ещё не
заведён; такого в норме быть не должно, и это повод написать нам, а не
подставлять своё значение.

Коды задаются на нашей стороне: у товара может быть свой код, иначе действует
общий код магазина. Значение может измениться — берите его из ответа при каждой
синхронизации, не кэшируйте надолго и не храните в своём справочнике как
константу.

### Фотографии

`images` — список картинок товара. Первая в списке основная, порядок значимый.

| Поле | Что это |
|------|---------|
| `url` | абсолютный адрес файла, всегда `https` |
| `hash` | SHA-1 **байтов** файла, 40 hex-символов |

`hash` нужен, чтобы не скачивать одну и ту же картинку повторно: если он не
изменился с прошлой синхронизации, файл тот же. Если картинку заменили, хеш
станет другим при том же адресе.

Пустой список означает, что у товара нет загруженной фотографии. Такой товар мы
и у себя не показываем.

> **Ключ для картинок не нужен и не должен использоваться.** Файлы отдаются по
> обычному публичному адресу — так же, как их видит покупатель на сайте. Токен
> нужен только для запросов каталога. Не подставляйте `?token=` в адрес
> картинки: он попадёт в ваш HTML, в логи CDN и в историю браузера.

Картинки размещены у нас. Мы никогда не отдаём ссылки на Billz — их условия
запрещают раздачу медиа с их CDN.

> В каталог попадают только товары, для которых у нас задана цена для Medicalka
> и включена выдача. Товар без назначенной цены не публикуется — так исключается
> продажа по нулевой цене.

## Шаг 3. Поиск

```
GET /products/search?q=Life E&limit=20
```

Ищет по названию, производителю, артикулу и штрихкоду одновременно.
Пустой `q` → `422`.

## Шаг 4. Остатки

```
GET /inventory?skip=0&limit=100
```

Возвращает только позиции, реально имеющиеся в наличии, поэтому
`is_available` всегда `true`: отсутствующих товаров в списке просто нет.

```json
{
  "items": [
    {
      "pharmacy_id": 1,
      "product_id": 25432,
      "quantity": "20.00",
      "price": "600000.00",
      "is_available": true
    }
  ],
  "total": 18
}
```

Остаток одной позиции:

```
GET /stock?pharmacy_id=1&product_id=25432
```

Если товара нет в наличии — **404**. Это ожидаемый ответ, а не ошибка: ваш
клиент превращает его в `None`.

`quantity` — свободный остаток: складской минус уже зарезервированный под
принятые заказы. То есть это количество, которое действительно можно продать.

Остатки обновляются из учётной системы каждые 5 минут.

## Шаг 5. Заказы

```
POST /orders?secret=<СЕКРЕТ>
POST /orders/{order_id}/status?secret=<СЕКРЕТ>
```

Medicalka принимает решение об одобрении или отклонении заказа в своём
кабинете, **до** этого запроса. Авторизованный `POST /orders` означает, что
Medicalka уже одобрила продажу: Fairhaven синхронно оформляет одну продажу в
Billz и только затем отвечает `200` со статусом `accepted`. Fairhaven не
показывает кнопок одобрения или отклонения и не создаёт Telegram-уведомление
при создании такого заказа.

Если `POST /orders` не поступил, Fairhaven ничего не делает. Поэтому внешняя
проверка может оставаться без результата, пока Medicalka не настроит или не
запустит исходящий запрос заказа.

Этот документ описывает контракт API, а не факт развёртывания или включения
продаж. После развёртывания оператор Fairhaven должен **отдельно** разрешить
запись в Billz (`BILLZ_WRITE_ENABLED=true`). Пока запись выключена,
`POST /orders` закрыт по безопасному сценарию: он не оформляет продажу и
возвращает `503` с кодом `mk_unavailable`, а не ложный успех.

Создание заказа:

```json
{
  "order_id": "3f1c...",
  "order_number": "MK-2026-005821",
  "customer": { "first_name": "Иван", "last_name": "Иванов", "phone": "+998900000000" },
  "delivery_type": "delivery",
  "delivery_address": "г. Ташкент, ул. Махтумкули",
  "items": [ { "product_id": 25432, "name": "SAMe 400мг", "quantity": 1 } ]
}
```

Ответ: `{"wc_order_id": 1042, "status": "accepted"}` — `wc_order_id` целое
число, как и остальные `id`.

**Повторная отправка того же `order_id` вернёт тот же стабильный целый
`wc_order_id`** и не создаст второй черновик, платёж или продажу — можно
безопасно повторить запрос при таймауте.

> Цена берётся из нашего каталога, а не из тела запроса. Поле `unit_price`,
> если вы его передадите, игнорируется: так исключается расхождение, когда у
> вас закешировалась старая цена.

Статусы передавайте **по вашему `order_id`** — тому, который вы сгенерировали
при создании заказа:

```
POST /orders/{order_id}/status?secret=<СЕКРЕТ>
{ "status": "paid" }
```

Наш `wc_order_id` здесь тоже принимается — обе формы работают, но хранить
достаточно свой идентификатор.

`paid` и `payment_confirmed` после успешного создания — совместимые
идемпотентные подтверждения уже проведённой продажи. Они возвращают тот же
`wc_order_id` и `processing`, но не создают повторный платёж или списание.
`received` и `accepted` остаются подтверждениями без изменения состояния.

Отмена уже проведённой продажи (`cancelled` или `cancelled_by_buyer`) вернёт
`422`. Возврат или возмещение — отдельный будущий учётный процесс, не операция
этого API.

Любое другое значение → `422`. Неизвестный идентификатор → `404`.

## Коды ответов

| Код | Значение | Что делать |
|---|---|---|
| 200 | успех | — |
| 401 | `{"code":"mk_unauthorized","detail":"…"}` — ключ неверный, неизвестный или отправлен не в тот эндпоинт | проверьте ключ и параметр (`token` / `secret`) |
| 403 | `{"code":"mk_forbidden","detail":"…"}` — ключ отключён на нашей стороне | свяжитесь с нами |
| 404 | `{"detail":"…"}` — объект не найден либо товара нет в наличии | ожидаемо для `/stock` |
| 422 | `{"detail":"…"}` — некорректные параметры запроса | см. текст `detail` |
| 429 | превышена частота запросов | повторите позже, см. ниже |
| 502 | `{"code":"mk_upstream_error","detail":"order could not be completed"}` — Billz явно отклонил операцию до подтверждённого эффекта | повторите тот же запрос с **тем же `order_id`** после паузы; новый id не создавайте |
| 503 | `{"code":"mk_unavailable","detail":"order processing is temporarily unavailable"}` — запись в Billz выключена, другая обработка ещё не завершилась либо результат требует сверки | ограниченно повторите тот же `order_id`; если `503` сохраняется, остановите автоматические повторы и обратитесь к оператору Fairhaven для сверки |

Ответы `502` и `503` намеренно обезличены: в них нет исходного ответа Billz,
учётных данных или внутренней диагностики. Постоянный `503` означает, что
оператор должен проверить включение записи либо вручную сверить неизвестный
результат с Billz до продолжения; такой случай автоматически не переигрывается.

## Частота запросов

Действующий лимит — **240 запросов в минуту на ключ**, плюс отдельный, более
строгий лимит на неудачные попытки авторизации (300 за 5 минут с одного адреса).
Оба рассчитаны так, чтобы рекомендованный режим ниже их не касался.

Рекомендуемый режим:

| Задача | Частота |
|---|---|
| Каталог `/products` | раз в час |
| Остатки `/inventory` | раз в 5 минут |
| `/stock` перед показом товара покупателю | по необходимости |

Постраничный обход каталога делайте последовательно, а не параллельно.
При `429` подождите и повторите — счётчик сбрасывается за минуты.

---

## Типовой сценарий

1. При старте — `/pharmacies` для проверки ключа.
2. Раз в час — обход `/products` постранично.
3. Раз в 5 минут — `/inventory`.
4. Перед показом товара — `/stock`, чтобы не продать отсутствующее.
5. Medicalka одобряет заказ в своём кабинете и отправляет `POST /orders` с
   действующим секретом. До `200 accepted` Fairhaven синхронно завершает одну
   продажу; поздний `paid` нужен только для совместимости.
