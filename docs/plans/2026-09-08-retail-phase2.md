# Retail phase 2 implementation plan

Goal: finish Yandex full retail order handling in the existing FairHaven admin and Telegram bot, audit Uzum against its own supplied contract, preserve Medicalka. Baseline 86b17c2 on codex/yandex-retail-20260908. Spec: docs/integrations/yandex-retail-design.md.

## Global constraints

- No Medicalka credentials, routes, settings, polling, approvals or legacy coercion changes. Preserve all existing keys. No second bot or panel.
- No SSH, production/partner requests, vault access, orders, BILLZ calls, Telegram sends, credential generation, activation or deployment by implementation workers. Only isolated local MongoDB and fake external transports. No .env reads; assert live credentials absent and disable dotenv before tests.
- No new dependencies, lockfile changes, unrelated refactors, weakening old tests, destructive git, stash, global configuration or nested agents. Workers are not alone: preserve others' edits, own only assigned files. Use apply_patch for edits. Root owns final verification, commit, push and release.
- Yandex Ready settlement is a stated local implementation assumption matching Uzum, not a claim of explicit accounting-event approval. Never enable BILLZ_WRITE_ENABLED. Fail disabled accounting before claiming operations, without labelling untouched orders uncertain.
- Public contract and accounting status must remain distinct. CANCELLED can arrive at any stage; post-sale cancellation preserves sale evidence and requires reconciliation, never automatic refund. paid attributes are metadata only.
- Preserve uzumSoldHolds records/semantics. Count independent yandexSoldHolds in every stock consumer. Atomic per-product settlement is not a claim of cross-product transactions or solved legacy allocation races.
- Use TDD: observe meaningful new tests fail against real code before implementation; literals/hand-checked expectations, real MongoDB for persistence/races, only external dependencies faked. Test current behavior, not source text.

Preserve existing Uzum implementation except the smallest shared snapshot integration needed to advance both sold-hold arrays atomically. Prefer small independent Yandex modules; do not generalize Medicalka or rewrite shared lifecycle machinery.

Existing phase-one rows must safely receive defaults without changing their immutable original request. POST exact/concurrent/restart retries keep same identity even after picking; receipt performs no reservation or sale. 2. Expose one Yandex lifecycle used by internal staff and public callbacks: list/get, decide and update picked composition. Ready invokes existing proven core sale boundary once; accept freezes and reserves approved picks. Reject releases only proven existing reservations/drafts. No invented Yandex acceptance timeout from Uzum's 15-minute rule.

5. Picking before freeze supports quantity reductions, line removals, catalog-backed replacement/addition; prices/names for replacement resolved on server from current published Yandex assortment. Existing incoming line price remains its accepted quoted price; never accept arbitrary supplied prices. Validate piece quantities, duplicates, totals, current publication/images/fiscal/measure metadata and availability before accepting. Unknown received items may be removed/replaced; do not reject otherwise valid receipt. Empty final picks cannot be accepted; operator can cancel. Original snapshot remains immutable. A version race or cancellation prevents late composition writes.
6. Register PUT /order/:orderId/status with application/vnd.eats.order.status.v1+json and JSON. Only status is required; allowed CANCELLED, TAKEN_BY_COURIER, DELIVERED. Validate optional reason/comment/updatedAt/platform/attributes types and bounds; RFC3339 timestamp when supplied. 204 with empty body only after durable receipt of the callback. Unknown IDs 404 error array; invalid fields 400 array; token errors remain reason object. Public GET status reflects fulfillment monotonically, with CANCELLED valid from any stage. No courier regression or resurrection. Repeated/stale callback is safe and cannot duplicate accounting. Partner courier callbacks require onboarding agreement; implementing handler does not claim agreement.
7. Persist cancellation and public CANCELLED immediately even when accounting is busy; callback cannot wait on external BILLZ beyond its deadline. Fence new accounting claims and pre-effect checkpoints against cancellation with Yandex-only predicates. Existing in-flight owner must observe cancellation; successful effect after cancellation is reconciled, never overwritten into READY. Restart must not lose pending cleanup; only proven safe cleanup can retry. Unknown external outcome retains ownership/reconciliation and never blindly retries payment. With BILLZ disabled, local no-effect cancellation still succeeds, while reserved cleanup remains visibly pending. Disabled acceptance must leave order untouched.
8. Add independent order-keyed Yandex sold holds. Transfer releases reservation and adds replay marker atomically per product using persisted quantities/ownership; a covering snapshot creates zero replay marker until durable finalization. Apply a monotonic snapshot watermark to both arrays in the same product update; preserve Uzum fields and replay guards. Count both in channel catalog, model availability, analytics, backend stock reconciler and every discovered shared consumer. Tombstone/deletion paths and cleanup protect both; cancellation after sale retains unresolved evidence.
